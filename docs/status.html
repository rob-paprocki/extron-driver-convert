Extron Driver Convert

Research into converting audio-visual device drivers between vendor formats: Extron .pkp (Global Configurator), Extron ControlScript .py, Crestron .pkg. Scope has grown to cross-platform bridging. Q-SYS both ways, Biamp Tesira → Extron, Crestron DM-MD controlled by an Extron processor.

Repo rob-paprocki/extron-driver-convert Main a31d707 Report 2026-10-25
In a sentence. Can a driver written for one AV control system (Extron, Crestron, Q-SYS, Biamp) be converted. Mechanically, correctly, and provably. Into another system's format, so a processor from vendor A can drive a device whose only released driver is for vendor B?

Why it exists

Vendors ship different driver formats for the same devices
Extron ships a .pkp (gzip over .NET NRBF, embedding a complete Python driver) and a plain-text ControlScript .py module. Crestron ships .pkg (zip over DLL with the driver definition as JSON inside). Q-SYS ships .qplug (Lua). Biamp Tesira ships Tesira text configs. The same physical device typically has drivers from only one or two of these, so the processor you own may not be able to control the device you own.
If translation works, one driver can serve any processor
A shared Command/Response intermediate representation lets any emitter target any format. Finding 05 is the proof-of-concept: two different vendor teams independently encoded the same Samsung display to byte-identical wire traffic, including the same undocumented firmware-bug workaround. The convergence says a shared IR exists to extract.

What the research actually produces

Tools, not a product
Everything is standard-library Python 3, no dependencies, no build system. One command per tool, deterministic, tested. The repo describes itself as "research with working tools."
An oracle for correctness
Acceptance is wire-string equivalence. do the bytes a translated driver sends match the shipped driver's bytes, command by command? Not line similarity, not file similarity. tools/wire_table.py is the oracle. 352 oracle pairs scored across 314 packages (finding 14).
A library of 20 numbered findings
Each finding is a reproducible result or a corrected mistake, with evidence paths and measurement methodology. See the Findings tab.

Open research questions

From STATUS.md "Open, in order of how much they matter" and ROADMAP.md §5 ("Open research questions and unmeasured claims"). These are the questions the project still wants answered.

1. Does an outsider-built .pkg load on a real Crestron processor?
Independent developers ship drivers built from the public NuGet DevKit, so the compile path is demonstrated. The resource-swap shortcut is not. Crestron Toolbox is obtainable; the gate is a processor or VC-4 instance plus the licence question. No amount of research substitutes for this.
Hardware + licence
2. Does a real i20 camera accept the synthesized .pkp commands?
Every reply parsed by the module so far came from documentation. No socket has been opened to a camera. 20028 is loader-verified but not yet uploaded.
Hardware
3. DM-MD IR and Relay: what does the chassis actually send?
Routing and ComPort passthrough are proven byte-exact (findings 28, 29). IR/Relay are stubbed because the chassis is silent on probes without instruments. A multimeter and an IR scope would answer this in a day.
Bench instruments
4. Catalogue coverage of Crestron's driver library
How much is extractable JSON-engine form vs V2 Entity Model vs V1 RAD? Two data points. The whole library is login-gated. Only answerable by sampling, and sampling needs credentials.
Credentials
5. A rendered command is not a polled one
A package can render, build, upload and send correctly and still never be asked anything. Polling is gated by PollingInterval carrying Enabled and by the project containing an instance of the command. GC compiles its poll list from panel feedback, monitors, and macros. Not from the driver's command list. Both gates were hit in turn and each looked like a bug in the package. Same "necessary but not sufficient" trap as the wire table, two gates further along.
Methodology note
6. Emulated feedback for devices that publish nothing
20028 adds 30 commands; 21 report live status, 8 are momentary with nothing to report, and only the lightbar is emulated. no inquiry exists in either vendor's driver or the documentation. One rule remains unsourced: Crestron declares none for GetFreezeFrame, so that parse follows VISCA convention.
1 remaining
7. Does Q-SYS plugin generation hold outside the DTP CrossPoint family?
Three families verified (DTP3, DTP, DTP2) with 27 model variants, all PCS-matched in Designer F6. Next test: a chassis-based family (XTP II CrossPoint, 16/32/64), which exercises dynamic matrix sizing the layout doesn't yet support. Then a non-matrix architecture (IN1608 presentation scaler).
Can test now
8. The runtime-resolvability frontier: what breaks beyond the four static checks?
Finding 14 §8: executing generated modules found five translator bug classes no static check had seen. A stripped @staticmethod and a re-entrant OnConnected are still invisible to the four static checks. Running the module remains the only honest runtime check.
Methodology note

Standing methodology notes

A negative claim needs positive evidence
Finding 08 twice asserted an endpoint was undocumented when it was not. Report a negative as "not found by method X," never as "does not exist."
Acceptance is the wire-string table, not file similarity
Line overlap between a package and its shipped module ranges 76%→38% while command tables stay near-identical.
Wire correctness is necessary but not sufficient
A module can carry a perfect command table and still raise AttributeError on a processor. 26 dangling self.X() references hid behind a near-perfect scorecard. Four static checks now; some bug classes still only visible by running the module.
Ask what the software actually reads
"Would GC accept our .pkp?" looked like a file-format question. GC reads a 61 MB catalogue built from an index, so discovery and parsing fail differently. And the library it reads is not the one in Program Files. Separate the steps before designing the test.

16

80085 is a SHA-256 mismatch. Extron's validator reimplemented in pure Python; 1,853/1,853 agreement with their own code on shipping packages (with the Guid table). GC no longer needed to check a package.

17

How a human writes one. A working integrator splices Extron's template from two vintages rather than authoring from scratch. The same instinct as our transplant.

18

The asset tree is the command surface. GC never asks the script what it can do. The i20 package goes 15 → 34 commands via object-graph synthesis, verified through Extron's own deserializer. Carries the negative-object-id trap.

19

Three-questions experiments. Crestron .pkg → ControlScript: 62 commands, 0 opaque. The .pkp's never-shipped Ethernet script translates with 11/11 shared commands and one wire difference. Docs-only generation covers 22/22 endpoints, though 15 of 33 wrote raw response dicts as status (fixed).

20

Automate VX, three ways. Extron GC + ControlScript call one identical set of 33 URIs. Crestron SIMPL wires 36 by join name. Native IP ID is VX2-only; the IV-SAM-VX2 symbol has 276 named joins. The richest surface of the three. 40 discrepancies cataloged, 21 live tests.
