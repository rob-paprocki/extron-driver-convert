## 1. Is the Automate VX ISO-record family (`StartISORecord`, `StopISORecord`, `ISORecordStatus`) deprecated?

**Repo's reading** (`findings/08-spec-vs-implementation.md:36-41`): "That pattern reads as deprecation, not omission" — based on all three endpoints having no dedicated doc page, contrasted with Crestron's demonstrated practice of recording removals in the changelog (`CallPlugin`, per `Whats-New.htm`, May 9 2025: "Removed support for depreciated CallPlugin API call").

**What I could check locally**: `reference/automate-vx-api/Whats-New/Whats-New.md` (harvested 2026-09-07, all 10 changelog entries from 2022-08-18 to 2025-07-01) — no entry mentions ISO recording at all, positive or negative. `reference/automate-vx-api/ENDPOINTS.md:68-82` records that of `GetAllStatus`'s 13 example sub-APIs, only `ISORecordStatus` is attested there; `StartISORecord` and `StopISORecord` do not appear **anywhere** in the harvested doc set, not even as example-body names. That is a stronger absence than the other 8 "undocumented sub-APIs" (`AutoSwitchStatus`, `OutputStatus`, `RecordStatus`, `CopyStatus`, `GetLayouts`, `LayoutStatus`, `GetRoomConfigs`, `RoomConfigStatus`), all of which at least surface inside `GetAllStatus`'s example response.

**Web research** (fetched 2026-09-23):
- `https://sdkcon78221.crestron.com/sdk/automate-vx-api/Content/Topics/Automate-API/Whats-New/Whats-New.htm` — same content as the local harvest, re-confirmed live; still no ISO-record mention in any direction.
- Searched `"Automate VX" OR "1 Beyond" "ISO record" OR "ISO recording" deprecated removed feature` — surfaced only product manuals (e.g. `docs.crestron.com/en-us/9487/.../System-Configuration.htm`) describing ISO recording as a **currently marketed, active feature** ("Program recordings and ISO recordings are saved to local storage at D:\Recordings\VX"; "ISO Record supports MJPEG MOV (30–200 Mbps)"). This confirms ISO recording the *feature* is alive; it says nothing about whether the specific `StartISORecord`/`StopISORecord`/`ISORecordStatus` **API** calls are still live, retired, or were ever public in the first place.
- Searched `"StartISORecord" OR "StopISORecord" Crestron Automate VX` — zero hits naming either call anywhere on the web, including Crestron's own domains.
- Fetched `https://sdkcon78221.crestron.com/sdk/Automate-VX-API/Content/Topics/Automate-API/API-Reference/StartRecord-API.htm` directly, to check whether ISO recording had been folded into the documented `StartRecord` call as a parameter (which would explain the missing dedicated ISO endpoints as a merge rather than a removal) — **no**: "No parameters are required for this API call," no ISO parameter, no mention of ISO recording at all.
- Fetched `https://www.crestron.com/release_notes/automate_vx_6.4.1.8_release_notes.pdf` (the current release notes PDF) looking for any ISO-record text — none found in the extracted text.

**Conclusion**: not found by method X (Whats-New changelog re-check, targeted web search for both call names, the StartRecord-merge hypothesis, and the current release-notes PDF). Unlike `CallPlugin`, there is no explicit "removed" changelog line for the ISO-record family — so the "deprecated" reading cannot be upgraded from inference to confirmed fact. But the total absence of `StartISORecord`/`StopISORecord` from every corner of the public doc set (not even example-body mentions, unlike the other 8 undocumented sub-APIs) is consistent with either (a) quiet deprecation without a changelog entry, or (b) the calls were always internal/private and never public API surface at all — the evidence available does not distinguish these. The repo's "deprecated, not omission" framing should be read as **plausible but still unconfirmed**, not strengthened by this pass.

## 2. What toolchain does Crestron `.pkg` "strategy B" (native driver source, not resource-patch) need?

**Repo's reading** (`findings/06-emission-and-generalisation.md:30-45`): the Samsung Serial DLL's `AssemblyRef` binds `mscorlib Version=3.5.0.0, PublicKeyToken 969db8053d3322ac` (the .NET Compact Framework token), and "Crestron's own docs mandate the EOL, Windows-only Visual Studio 2008 + WinCE/.NET CF toolchain for any 'commercial application or 3-Series control system' driver." A verifier left UNCERTAIN whether *this* driver is bound by the VS2008 path or the residential/4-Series VS2019 path.

**Web research** (fetched/searched 2026-09-23):
- `https://support.crestron.com/app/answers/detail/a_id/1145/` ("SIMPL# Pro - Why is Microsoft Visual Studio 2008 Required?") — confirms VS2008 is required **for SIMPL# Pro**, because .NET Compact Framework 3.5 (needed for 3-Series **programs**) is not supported by later Visual Studio releases. This is the source of the repo's VS2008 claim, but it is about SIMPL# *programs*, not the Certified Drivers SDK specifically.
- `https://sdkcon78221.crestron.com/sdk/Crestron_Certified_Drivers_SDK/Content/Topics/Driver-SDK-V1/Create-a-Driver/Create-a-Project.htm` (Driver SDK V1 / RAD Framework) — states the toolchain as **"Visual Studio 2019, 2022, or 2008"**, a `.NET Framework Class Library` project, "any version after .NET Framework 3.5" (4.7.2 shown as the example), and NuGet packages `Crestron.SimplSharp.SDK.Library`, `Crestron.DeviceDrivers.DevKit`.
- `https://sdkcon78221.crestron.com/sdk/Crestron_Certified_Drivers_SDK/Content/Topics/Driver-SDK-V2/Create-a-Driver/Create-a-Project-V2.htm` (Driver SDK V2 / Entity Model) — same toolchain list (VS2008/2019/2022), same NuGet packages plus `Crestron.DeviceDrivers.ManifestUtil`.
- `https://sdkcon78221.crestron.com/sdk/Crestron_Certified_Drivers_SDK/Content/Topics/Overview/SDK-Architecture-Versions.htm` (via search snippet, not fetched directly — see caveat below) — states V2 (Entity Model) is available "as of Crestron Drivers SDK version 21.x" alongside the older V1 (RAD Framework); "Platform drivers cannot contain both Driver SDK V1 and V2 child device types"; both frameworks are said to support 3-Series **and** 4-Series over IR/Serial/Ethernet/HDMI(CEC).
- Attempted `https://sdkcon78221.crestron.com/sdk/Crestron_Certified_Drivers_SDK/Content/Topics/Overview/SDK-Comparison-Tables.htm` for an explicit VS-version-by-target-series matrix — fetched, but it turned out to be a **firmware/SDK-framework-version compatibility table (2.x–28.x), not a VS-version/target-series matrix** — this specific cross-reference (which VS version is mandatory for which target series) was not found by this method.

**Spot-check by the orchestrator (2026-09-23).** Re-fetched the V1 Create-a-Project page: the Visual Studio versions, the project type and "any version after .NET Framework 3.5" are verbatim, but **the page says nothing about 3-Series, 4-Series or the Compact Framework**. So the series claim below rests only on the Architecture page's search snippet, not on a fetched page.

**Conclusion — refutes the strict framing**: the current Crestron Certified Drivers SDK docs do **not** gate 3-Series driver development behind VS2008/.NET CF the way finding 06 implies; both V1 and V2 architectures accept VS2019 or VS2022 with a normal desktop `.NET Framework Class Library` project (>=3.5, 4.7.2 shown), for either 3-Series or 4-Series. VS2008 remains *an accepted option*, and is separately confirmed mandatory for **SIMPL# Pro programs** targeting 3-Series (the CF-3.5 requirement), which is a related but distinct Crestron product from the driver SDK. This does not fully resolve the verifier's UNCERTAIN: it is not established how (or whether) a VS2019/2022 project can be made to emit an assembly bound to the CF `mscorlib 969db8053d3322ac` token the way the Samsung DLL is — no page found addresses that specific mechanic, so "which toolchain built *this* driver" is still open, but "which toolchain is *required* today" is answered: **VS2019/2022 + the `Crestron.SimplSharp.SDK.*` / `Crestron.DeviceDrivers.DevKit` NuGet packages, targeting `.NET Framework` (not CF) — for both 3-Series and 4-Series, per current docs.**

## 3. How do Control4 and Savant driver houses ship drivers across vendors?

- **Control4**: drivers are `.c4z` archives (zip-based, produced by the `drivers-driverpackager` pipeline: Lua source + an XML manifest, with Lua optimization/encryption baked into packaging) built with the **DriverWorks SDK** and the **DriverEditor** IDE, per `https://docs.control4.com/help/c4/software/cpro/dealer-composer-help/content/composerpro_userguide/using_drivereditor.htm` and `https://control4.github.io/docs-driverworks-fundamentals/`. Widely cited third-party figure: "OS 3 ... supports over 14,000 third-party device drivers" (from the earlier platform-comparison search results, not a primary Control4 source — flagged as such).
- **Savant**: drivers/profiles are distributed through a dealer portal and built on Savant's proprietary **RacePoint Blueprint** software / **TrueControl** stack (`https://www.northbt.com/doc/driver/Savant%20Application%20Note.pdf`; `https://support.symbioav.com/hc/en-us/articles/203339387-Savant-TrueControl-User-Guide`). No public SDK documentation equivalent to Control4's DriverWorks docs was found by this method — Savant's driver format appears closed/dealer-portal-only, not self-serve like Control4's. Third-party estimate: "~3,000–5,000 third-party integrations" (same caveat as above).
- **Cross-vendor driver houses**: `https://drivercentral.io/platforms/` is a marketplace listing drivers for **Control4, ELAN, RTI, URC, Q-SYS and Crestron** side by side; `https://drivercentral.io/chowmain-ltd/` lists Chowmain as a vendor there shipping to **Control4, Crestron, Crestron Home, ELAN/Nice, Fibaro, Q-SYS, RTI, Savant and URC** (per Chowmain's own marketing copy surfaced in search — the direct fetch of `https://chowmain.software/for-manufacturers/driver-development` returned only a page heading, no body text, so this is sourced from the search snippet, not a primary-page quote). **What the search did *not* show**: any description of a single shared source artifact compiling to multiple vendor-native formats (`.c4z` for Control4, whatever Crestron's driver-SDK output is, a Savant Blueprint profile, etc.) from one codebase. The pattern that *is* evidenced is a marketplace/storefront (DriverCentral) aggregating **separately-built, per-platform** drivers from the same development house — i.e. one team, several codebases, one storefront, not one codebase compiled N ways. This is the strongest answer available; a same-source-multi-target claim would need direct confirmation from a driver house (e.g. an engineering blog post or interview), which was not found by this method.

## 4. Extron Global Configurator Plus vs Pro — same `.pkp` library, or different?

- `https://www.extron.com/article/sw_79-544-01` and `https://www.extron.com/product/software/gcpro` — both **blocked** (bot-defense rejection on the article page, HTTP 403 on the product page). Matches `CLAUDE.md`'s note that `www.extron.com` returns filtered/empty responses to automated fetches; recorded as **not found by method X (direct fetch, blocked)**.
- Google-cached search snippets of those same two pages (via `WebSearch`, not a direct fetch, so treated as lower-confidence secondary evidence) state: "Global Configurator Plus is ideal for smaller applications requiring one control processor and one control interface. ... Global Configurator Professional is suited for applications requiring multiple control processors, enhanced functionality, and advanced configuration. Access to Global Configurator Professional requires ECP Certification. ... Global Configurator Professional offers a library of enhanced, Extron Certified device drivers..." — this implies the two apps' *available driver catalogues* differ (Pro gets an "enhanced, Certified" set gated behind ECP Certification), even though nothing suggests the `.pkp` **file format itself** differs between them.
- `https://www.manualslib.com/manual/1400212/Extron-Electronics-Medialink-Mlc-Plus-50.html?page=50` (an MLC Plus 50 user manual mirror, fetched successfully — not extron.com) confirms the file-type distinction directly: **`.pkp` — "a driver package file"**, separate from **`.gcplus`** ("a Global Configurator Plus configuration file") and **`.gcpro`** ("a Global Configurator Professional configuration file"). This is a primary-source (Extron manual text, mirrored) confirmation that `.pkp` is *one* package format shared by name across both products' file-type glossary — it does not by itself prove the two apps ship an identical driver *set*, only that they use the same package *format*.
- Earlier search-only result: "Driver packages contain three years of third party drivers as well as all Extron drivers, and if other drivers are needed outside of this range, they must be downloaded separately" (source page not re-verified by direct fetch — treat as unconfirmed detail, included for completeness).

**Conclusion**: `.pkp` reads as **one shared package format** used by both Global Configurator Plus and Professional (confirmed via the mirrored manual, since extron.com itself was unreachable). Whether the two apps' **driver libraries** (i.e., which `.pkp` files each app's catalogue actually offers/ingests) are identical or Pro-is-a-superset could not be confirmed directly — the only evidence is a search-engine snippet of an extron.com page this session could not itself fetch, describing Pro's driver library as "enhanced" and "Certified" relative to Plus's. Recorded as **not found by direct method** (extron.com blocked both ways); the secondary snippet evidence points toward "same format, different available catalogue," matching the repo's open question in `findings/00-open-questions.md:13` ("do GC Plus and GC Pro differ?") without fully closing it.
