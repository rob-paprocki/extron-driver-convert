# Answers

**1. Crestron IP driver in, Extron out.** The **ControlScript `.py` is demonstrated** — a Crestron IP `.pkg` was mechanically converted into a 62-command, zero-opaque, compiling ControlScript module whose wire content matches Extron's own IP driver exactly on 5 of the 8 JSON-RPC methods both vendors implement — but the **`.pkp` is not**: only the NRBF *wire format* is proven writable (byte-identical round-trip on all four samples), and nothing has ever assembled a package graph from scratch or had one accepted by Global Configurator.

**2. Writing the .pkp's missing Ethernet control into a .py.** **Done and measured**, not merely plausible: `tools/pkp2cs.py` translated the Samsung `.pkp`'s ethernet script into a compiling 392-line ControlScript module with 11/11 commands present and 10/11 wire-identical, with one command (`MultiviewCommand`) carrying a live `AttributeError` from a translator pruning bug that a human must patch before deployment.

**3. Docs-only generation.** **22 of 22** documented endpoints Extron actually implements, **plus 5 of 5** example-only sub-APIs, reproduced from documentation alone — but the generator is blind to **6 endpoints Extron calls that appear nowhere in the corpus**, and **15 of its 33 commands** silently mishandle their response payload, so the result would largely *command* the device while largely failing to *read* it, and a reviewer without hardware can see the missing commands but cannot see the broken ones.

## Q1a — Generating a .pkp: the format is writable, the package is not proven

`experiments/nrbf_writeback/nrbf_write.py` re-serializes a parsed `.pkp` back to bytes. Running it on all four samples prints `byte-identical: True` at identical sizes (Samsung 649,389; DSC 629,733; DTP3 664,380; Automate VX 1,290,096), and `python3 experiments/nrbf_writeback/test_nrbf_write.py` reports `16/16 passed`. A targeted mutation — changing DSC object 37's `_author` string — survives re-serialize and re-parse under the *unmodified* `tools/pkp_dump.py` with object count (8840), record-type histogram, and sibling references unchanged. That works because NRBF has no absolute-offset pointers: every cross-reference is a logical object id, so a length change needs no fix-ups.

Two facts from that experiment matter more than the round-trip itself. First, `pkp_dump.py`'s JSON graph is *provably insufficient* to write from — `tools/pkp_dump.py:542-553` emits only `{$type, class, members, library, metadata_ref}` and never carries per-member `BinaryType`/primitive width, and it reports untyped `SystemClassWithMembers` records (all 1,171 `System.Guid` instances in the DSC sample) as `SystemClassWithMembersAndTypes`. The writer therefore works from an order-preserving parse *trace*, not the JSON. Second, the writer refuses rather than guesses on the one shape it can't verify (`BT_Primitive` + `PT_String`, absent from all four samples).

Caveat on citations: two byte offsets in that experiment's write-up are wrong — the `MemberTypeInfo` run starts at `0x39d`, not `0x39e`, and the duplicated `MemberPrimitiveTyped` record at `0x7c9f`, not `0x7ca6`. The underlying bugs are real (reverting either fix breaks the round-trip; the duplicate-write bug adds 797 bytes to DSC), but treat those two offsets as unreliable.

**Remaining work:** build a graph constructor that emits a valid `DriverModelAsset`/`DriverFileAsset` set from nothing — GUID allocation, asset cross-references, schema/version fields, the `.pkp` container's non-NRBF parts — then get Global Configurator to open it. **Hardest obstacle:** not the serializer, it's that *nothing in this environment can tell you whether GC accepts the result*. Every acceptance invariant beyond "well-formed NRBF" is currently unknown, and the failure mode of a rejected package is a silent GC error with no oracle to bisect against. Until a GC install is in the loop, .pkp generation is unproven — mutating a real `.pkp` (retarget a model, rename, swap a script blob) is the demonstrated capability today.

## Q1b — Generating the .py from a Crestron package: demonstrated

`experiments/crestron2cs/crestron2cs.py` resolves the Samsung IP `.pkg`'s LegacyWrappers Template/Transformation/Rule graph and emits `out/generated_controlscript.py` (1,169 lines — the "1187" figure in the source report is wrong). `wire_table.extract_table` on it returns 62 commands / 0 opaque markers, the same zero-opaque bar as Extron's own scripts; 14/14 unit tests pass.

Name-keyed `diff_tables` is the wrong oracle here — only `Power` and `Volume` share identifiers, because the generator mirrors Crestron's atomic command granularity rather than Extron's editorial grouping. Method-keyed comparison (`out/semantic_comparison.json`) gives the real picture: 17 distinct JSON-RPC methods, 8 in both, 8 Crestron-only, 1 Extron-only. Of the 8 shared, `powerControl`, `muteControl`, `inputSourceControl`, `channelUpDnControl` all report `wire_values_match: true` with identical value domains (`{HDMI1..HDMI4, TV}`, `{powerOn, powerOff}`), `directVolumeControl` matches on the Set direction, and `remoteKeyControl`'s 19 Extron values are a proper subset of Crestron's 30. The remaining two diverge for reasons that are not translation errors: `createAccessToken` differs only in id policy (Crestron's manifest declares `MonotonicIntegerId` 1–127; Extron hardcodes `'id': 1` at all 13 call sites), and `multiviewControl` reflects two commissioning models (Crestron hardcodes `My Multi View 1/2/3`; Extron reads an installer-set free-text status).

The one Extron capability with no Crestron counterpart — `pictureSizeControl`/AspectRatio — is blocked by a bug in *Crestron's own manifest*: exactly 1 of 77 `Commands[]` entries (`SetVideoConfiguration`) spells the key lowercase `info`, and its block does contain `method: pictureSizeControl`. That is a dead command as authored, not a protocol gap.

Two things the write-up gets loose: the Get*-consumed-as-Update count is 7, not "~9", and `GetVideoConfiguration` is orphaned by the same manifest bug without appearing in the skip list. Also, `wire_table` is architecturally blind to the one real byte-level divergence found: Crestron's manifest quotes volume (`"volume":"{Volume}"`) where Extron sends a bare number.

**Remaining work:** the emitted module is a *measurement artifact*, not a driver. Crestron's Rule engine is not executed — `CommandSequence` chains, `NeedsPowerOn`/`RequireAccessToken` blocking rules, and response-routing/`WriteStatus` plumbing are unimplemented (only the 6× WakeOnLan-before-power-on rule was folded in explicitly). **Hardest obstacle:** that rule/state engine. The request bodies are solved; converting Crestron's declarative rule graph into ControlScript's imperative polling/state model is the actual work, and it has no oracle — `wire_table` only inspects request construction, so nothing currently measures whether the runtime behaviour is right.

## Q2 — The missing Ethernet module: done, with one patch outstanding

`pkp2cs.discover_jobs()` on the Samsung `.pkp` returns exactly two jobs (serial, 6 models, 29,180 bytes; ethernet, 6 models, 37,190 bytes). `translate_job()` needed **zero changes to `tools/`** — the HTTP dialect path built for Automate VX (`tools/pkp2cs.py:1071-1160`) detected `Extron2.HTTPDriver` and emitted the module directly. It compiles under `py_compile`. The diff against the `.pkp`'s own embedded script: `only_in_a: []`, `only_in_b: ['ConnectionStatus']` (boilerplate Extron itself injects), 11 shared, **1 difference**. AspectRatio, AudioMute, ChannelStep, Input, Keypad, MenuNavigation, MultiviewString, Power, RefreshToken and Volume are wire-identical including the `createAccessToken` handshake.

The one defect is real and reproducible: the generated `SetMultiviewCommand` calls `self.ReadMultiviewString(qualifier, 'Emulated')`, which `pkp2cs`'s write/read-wrapper pruning rule (`tools/pkp2cs.py:590-604`) deleted because it *looks* like a pure status accessor — except this driver calls it cross-command from another command's Set body. Instantiating the class and calling the method raises `AttributeError: 'DeviceClass' object has no attribute 'ReadMultiviewString'`. It produces **no residual warning at all**, which is the worrying part.

Two corrections to the source report. There is a **second** dangling reference from the same root cause: the translated `OnDisconnected` calls the deleted `self.__ResetLiveStatus()`. It is harmless only by accident — the generated class contains *duplicate* `OnConnected`/`OnDisconnected` definitions (lines 255-259 real, 261-268 synthesized), and Python's later definition wins, so the synthesized one runs. That also means the claim "the synthesized handlers match the original no-op design" is **false**: the live handler sets `connectionFlag`, calls `WriteStatus('ConnectionStatus','Connected')` and resets a counter, where the original `OnConnected` was `pass`. The duplicate-definition pattern reproduces on the Automate VX `.pkp` too, so it is pre-existing translator behaviour, not specific to this device.

**Remaining work:** fix the pruning rule to keep a `Read<X>`/`Write<X>` wrapper referenced from any other command body; fix duplicate handler emission; then run under a real ControlScript host. Nobody has executed this against `extronlib` or the display — this is AST-level fidelity only. **Hardest obstacle:** the absence of a runtime oracle. `wire_table` measures request bodies and cannot see method deletion, duplicate definitions, or handler shadowing — every defect found here was found by reading code or by instantiating the class by hand, and there is no reason to assume that list is complete.

## Q3 — Docs-only generation: 22/22 and 5/5, and a payload problem

From `reference/automate-vx-api/` alone, `experiments/docs_only/generator.py` produced a module covering **both=22, extron-only=0, generated-only=10, total-official=32** and sub-APIs **both=5, generated-only=4, total-listed=9** (`endpoint_crossref.txt:133-134`). It implements 10 documented endpoints Extron chose not to build (CopyFiles, GetAllStatus, Macro, Restart, …) — those are Extron's product decisions, not generator gaps.

**The documentation's limit** is exactly 6 endpoints (`endpoint_crossref.txt:135`): the 5 already known (`StartAutoSwitch`, `StopAutoSwitch`, `StartISORecord`, `StopISORecord`, `Wake`) plus a new one found here, `api/ChangeRoomConfiguration`, called at `samples/Automate VX/Controlscript/onebynd_sm_Automate_VX_Series_v1_0_11_0.py:282`. It appears exactly once in the whole corpus — inside an unrelated malformed cURL example at `reference/automate-vx-api/API-Reference/Macro-API.md:57` — so `ENDPOINTS.md`'s own sub-API catalogue misses it. That is a genuine gap in our reference doc worth folding back in.

**The generator's limits** are separate and larger. Range validation is applied inconsistently (CallCameraPreset guards 1–255; ChangeLayout's documented A–Z, ForceChangeRoomConfig's 1–99, ManualSwitchCamera's 1–255 are unguarded). `GetAllStatus-API.md` states verbatim that each nested `response_body` "is of type string and must be deserialized by the client" — the generated `UpdateGetAllStatus` never does the second `json.loads`. And the big one: `gen_simple_update()` passes the raw HTTP response dict straight to `WriteStatus` with no field extraction. `grep -n "self.WriteStatus(.*res, qualifier)"` matches **15** of the module's 33 commands — not the 7 or 8 the experiment's own write-up implies. That is nearly half the module. Ambiguity in the docs is real but minor by comparison: every parameter the prose calls "Integer" is shown quoted in the same page's example block, several examples are malformed JSON (`CallCameraPreset-API.md` has a stray unmatched quote), and trusting the prose produced the two confirmed type diffs against Extron (`ptDir`/`zDir` as int vs Extron's `'0'..'7'`).

One integrity caveat: this run's blinding was imperfect. An early over-broad file read exposed Extron's `Commands` dict and the bodies of `SetCameraPresetRecall`/`SetCameraPresetSave`. The doc-gap set stayed clean — none of the 6 invisible endpoints appear anywhere in the generated module — but the two camera-preset commands' parameter/qualifier design is compromised corroboration, not independent evidence.

**Would it control the device?** Partly, and asymmetrically. The Set direction is mostly sound — right URLs, right bodies, modulo the int-vs-string question that only hardware can settle. The Update/feedback direction is broadly broken: 15 commands hand a dict where the status system expects a scalar, and they do it while returning HTTP 200 with valid JSON on the documented success path.

**Could a reviewer tell what's missing without hardware?** For the absent commands, yes and cheaply — there is no method named `Wake` or `AutoSwitch` anywhere in the file, and `analyze_endpoints.py` mechanically produces the coverage table in seconds. For the broken ones, no. Nothing about `UpdateAutoSwitchStatus` looks wrong: it cites a real documented endpoint, parses valid JSON, and never raises. Only comparing the `WriteStatus` argument against what a downstream GUI tag expects would reveal it — and that comparison requires knowing the device, which is the thing docs-only generation is trying to avoid needing.

**Remaining work:** make response-shape extraction explicit and required (declare per endpoint what field carries the value, fail loudly when unknown), apply documented domains uniformly, and add a second docs pass that harvests endpoint URIs from *examples* across all pages, not just `GetAllStatus`'s. **Hardest obstacle:** the silent-success failure mode. Docs-only generation reliably produces code that *runs*; nothing in the docs tells you what the response means well enough to know when the code is quietly wrong, and no static check can distinguish "returns a dict correctly" from "returns a dict where a scalar was needed."

## What this adds up to

Two of the three are buildable now. Crestron `.pkg` → ControlScript `.py` and `.pkp` → ControlScript `.py` both work end-to-end today at measured, high fidelity, with concrete named defects rather than unknowns; the shared gap is runtime — rule/state plumbing and the total absence of a behavioural oracle, since `wire_table` deliberately measures only request construction. Writing a `.pkp` is one proven layer (bytes) and one unproven layer (package validity), and the unproven layer cannot be closed without Global Configurator in the loop. Docs-only generation clears the coverage bar convincingly and fails on semantics, in the specific way that is hardest to catch by review.
