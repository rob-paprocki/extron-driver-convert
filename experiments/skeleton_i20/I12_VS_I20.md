# R21 — IV-CAM-I12 vs IV-CAM-I20: is the shared 33-command surface valid on both?

Research only. No code changed. Scope: this file.

## What was checked and how

- `reference/crestron-visca/COMMANDS.md` — Crestron's VISCA command reference,

  `reference/crestron-nextgen-cameras/pages/Topics/NextGenCameras/Specifications/I12Specs.md`
  — the two per-model spec sheets (note: the I12 one only exists in the
  `crestron-nextgen-cameras` harvest, not alongside its I20/P20 counterparts in

- `reference/crestron-visca/Presenter-Tracking-Settings.md` and

  `samples/Crestron 1 Beyond IV-CAM-i12_i20/Crestron/Camera_Crestron-1-Beyond_IV-CAM-I20_IP/Camera_Crestron-1-Beyond_IV-CAM-I20_IP.dat`
  (JSON manifest) and the sibling `.pkg`/`.dll`.
- `experiments/skeleton_i20/build_i20.py` (Commands dict, `NEW_METHODS`,
  provenance comments) and `experiments/skeleton_i20/build_i20_assets.py`
  (`PLAN`/`DECIMAL_PLAN`) — where our 33 commands and their bytes/ranges

- `experiments/skeleton_i20/i20_wire_table.txt` — the flat table
  `resolve_visca.py` extracted from Crestron's compiled SchemaVersion 2.0

- `tools/pkp_dump.py` on the donor

driver artifact, because no such artifact exists in this repo.

### 1c. The Intelligent-Switching (`c2`) family — commands 8, 12, 16 — is arguably I12's, not I20's

`IntelligentSwitching`, `CameraOutput` and `CameraConnectionStatus` were all
built from `reference/crestron-visca/COMMANDS.md` §9
(`VISCA-Intelligent-Switching-Commands.md`), which itself carries **no**
per-model gate on any of its rows (COMMANDS.md:461-476). But three independent
facts point the other way from what the package currently does (these three
commands ship attached to *both* models, §3):

1. **I12Specs.md:65-69**: "Camera Processing / Intelligent Video Functions /
   Group Framing, Presenter Tracking, **Intelligent Switching**."
2. **IV-CAM-I20-Specifications.md:65-69**: "Camera Processing / Intelligent
   Video Functions / Presenter Tracking, Group Tracking, Preset Zones" — no
   mention of Intelligent Switching, Group Framing, or Camera Output/Camera
   Connection Status anywhere on the I20 spec page.
3. **Reserved-Presets.md:80-92**: presets 84/85/86 — a *second*,
   parallel encoding of the same function family via `CAM_Memory` presets
   rather than the `c2` command set — are scoped "IV‑CAM‑I12" (84) and
   "IV‑CAM‑I12, and IV‑CAM‑I12D‑B" (85, 86). No preset in this range is scoped
   to I20 anywhere in the table.

None of this proves the `c2` family is I12-*exclusive* — the
VISCA-Intelligent-Switching-Commands page itself is unqualified — but every
model-scoped signal this harvest has on Intelligent Switching names I12 and
never names I20. **If anything, the open question this raises is the
opposite of the one asked**: whether `IntelligentSwitching`/`CameraOutput`/
`CameraConnectionStatus` belong on the *I20* model entry, not whether they
belong on I12's.

Also note: our `IntelligentSwitching` "Resume" value sends the `c2` route
(`8x c2 01 08 00 ff`, build_i20.py NEW_METHODS `_cmd_SetIntelligentSwitching`)
rather than the documented I12-specific preset 84 (`8x 01 04 3F 02 54 FF`,
decimal 84 = `0x54`). Both are independently documented; only the preset-84
route carries an explicit I12 citation. See §2.

### 1d. ZoomPosition — the wire range is identical, but the ratio it means is not

`ZoomLevelToPosition`'s target range, `0-16384` (`build_i20_assets.py:483`,
`build_i20.py:334,343`, `0x4000` = 16384 decimal), is **not I20-specific**:
ZOOM.md:114-115/347-348 observes both the 12x and 20x lookup tables in
COMMANDS.md §6 run end to end from hex `0000` to hex `4000` regardless of the
lens' optical ceiling. So the wire range `0-16384` is valid for I12 exactly as
built, unchanged.

What *does* differ is which lookup table a given position value corresponds
to: ZOOM.md:136-146 ("Which camera uses which table") states I12 uses the 12x
table (COMMANDS.md:304-320) and I20 the 20x table (COMMANDS.md:321-344) — so
position `0x4000` is I12's *12x* and I20's *20x*, and every intermediate value
maps to a different optical ratio between the two tables (non-linear in both,
per ZOOM.md:116-124). Our built driver never performs this position-to-ratio
conversion — `_cmd_SetZoomPosition`/`_cmd_UpdateZoomPosition`
(`build_i20.py`, "Begin ZoomPosition") pass the raw 16-bit position straight
through with no lookup — so **no code change is needed for I12's wire
behavior**; this only matters the day something (a driver help string, a UI
label) claims a position value means "Nx" without checking which model it's
talking to.

### 1e. PanTiltAngle / PanAngleStatus / TiltAngleStatus — no I12 difference found

Both spec pages give byte-identical figures: "Pan: -130° — 130°, Tilt: -30° —
90°" and "Pan: 0.2° — 90°/s, Tilt: 0.2° — 70°/s" appear verbatim on both
I12Specs.md:45-51 and IV-CAM-I20-Specifications.md:45-51. The degree-to-unit
conversion factor these commands assume (`±2448`/`±1296`) is not itself
documented for *either* model — COMMANDS.md's own "1 angle = 14.4" fragment
(COMMANDS.md §4 note, reproduced at lines 228-234) is flagged there as
probably a misplaced table annotation, and COMMANDS.md §11 (lines 525-533)
only sanity-checks it arithmetically, without confirming zero point or sign.
So this command's confidence level is unchanged between I12 and I20 — neither
better nor worse documented on one model than the other.

### 1f. IndicatorLight — wire bytes are model-agnostic; the physical geometry citation says "I12-B", not "I12"

VISCA-Lightbar-Commands.md:439-442 gives the byte FORMAT
(`8x c1 ** ** ** ** ff`, brightness/color packing) with no model
restriction — it is used identically regardless of camera. The only
model-varying fact on that page is **segment count**, and it is stated as:

> "IV-CAM-P12 and IV-CAM-P20 series cameras: four segments of 4 (16 lights)."
> "**IV-CAM-I12-B** and IV-CAM-I20 series cameras: two outer of 4 + two inner
> of 3 (14 lights)." (VISCA-Lightbar-Commands.md, "Available Lightbar
> Segments" section)

Note the hyphenated **"IV-CAM-I12-B"**, not plain "IV-CAM-I12" as our package
names it (`build_i20.py:963`, `b.replace_string(358, "IV-CAM-I12")`). Whether
plain I12 and "I12-B" are the same physical light bar, or whether I12-B is a
distinct SKU (compare `Reserved-Presets.md`'s separate, and clearly distinct,
"IV‑CAM‑I12D‑B"), is **not stated anywhere in the harvested set** — reported
as a gap, not assumed either way. Since the wire bytes are 4 fixed positions
regardless of physical light count, `IndicatorLight` is wire-valid for I12
either way; only the resulting visual pattern is potentially uncertain.

## 2. I12-only features absent from our driver

From Reserved-Presets.md's full table (lines 30-179), the presets explicitly
scoped to I12 (alone or with I12D-B) that our 33 commands do **not** reach:

| Preset (dec/hex) | Function | Cameras | Bytes | In our driver? |
|---|---|---|---|---|
| 84 / `0x54` | Resume Intelligent Switching | **IV‑CAM‑I12** only | `8x 01 04 3F 02 54 FF` | No — `IntelligentSwitching`'s "Resume" instead sends the `c2` route (§1c) |
| 85 / `0x55` | Pause Intelligent Switching, output Host camera feed | IV‑CAM‑I12, IV‑CAM‑I12D‑B | `8x 01 04 3F 02 55 FF` | No — no command names "Host camera" specifically; `CameraOutput`'s numeric IDs 1-5 have no documented mapping to "Host" |
| 86 / `0x56` | Pause Intelligent Switching, output Presenter Tracking camera feed | IV‑CAM‑I12, IV‑CAM‑I12D‑B | `8x 01 04 3F 02 56 FF` | No — same gap as 85, for the Presenter Tracking camera |

(Reserved-Presets.md:90,98 both note tracking state is *unaffected* by 85/86 —
`Preset 81` must be sent separately to pause tracking itself — a semantic our
`CameraOutput` composed command does not attempt to replicate.)

Presets 87-89 (Group Framing enable, "Unavailable", Speaker Tracking;
Reserved-Presets.md:102-118) are scoped to **IV‑CAM‑I12D‑B only**, not plain
I12 — out of scope for this package's I12 model entry, and correctly absent.

**A separate, more basic gap**: `Change-the-Camera-Mode.md:5,33-39` states
that plain IV-CAM-I12 (and I12D-B) can switch between "Presenter Tracking" and
"Group Framing" modes, and shows a screenshot explicitly captioned "the i12
camera in Group Framing mode" (line 35) — so I12 does have a group-framing
capability. But **no VISCA byte sequence for triggering that switch on plain
I12 is documented anywhere in the harvested set**: Reserved-Presets.md's only
"Enable Group Framing" preset (87) is I12D-B-only, and TrackingMode's presets
82/83 are I20-only (§1b row 2). This is reported as "not found by method X" —
Change-the-Camera-Mode.md documents the *feature* (as a Camera-Manager-software
UI action) without documenting a *VISCA command* for it on plain I12 — not as
"I12 cannot do this."

`CAM_MountMode` (Stand/Ceiling, COMMANDS.md:225-226) is explicitly
"IV-CAM-P12 and IV-CAM-P20 only" — not an I-series feature at all, on I12 or
I20, so its absence here is expected and not an I12-specific gap.

## 3. What the donor and our package actually carry per model (`pkp_dump.py`)

### 3a. The donor, `1bynd_19_4743_v1_0_1.pkp`

Two `DriverModelAsset` objects, ids **108** and **109**, named by strings 358
and 368. Read directly off the *unmodified* donor (before `build_i20.py`'s
`replace_string`), those strings are:

```
358 -> "PTZ-IP12"
368 -> "PTZ-IP20"
```

Both models' `_scriptFileName`/`_scriptClassName` point at the exact same
string objects (354/355 = `364`/`365` = `"_1bynd_19_4743.py"` /
`"_1bynd_19_4743"`) — i.e. Extron's own donor already uses **one script for
two models**, the same pattern `build_i20.py` follows for I12/I20.

Each model has its own `Commands` sub-asset (object **832** for model 108,
object **835** for model 109) with its own child-collection array (**1333**
for 832, **1339** for 835) — genuinely separate array objects. But the
*elements* inside those two arrays are `$ref`s to the same 15
`DriverCommandAsset` objects (ids **90-104**), just in a different order:

```
model 108 (PTZ-IP12) array 1333: [104, 95, 102, 99, 93, 98, 97, 101, 91, 100, 96, 103, 90, 94, 92]
model 109 (PTZ-IP20) array 1339: [103, 95, 102, 99, 104, 93, 98, 97, 101, 91, 100, 96, 90, 94, 92]
```
— same 15-element *set*, same underlying command objects, different sort
order per model.

A third collection, object **30** ("DriverCommands", parent object **1**, the
package root) is the actual owning pool: its array (object 85) holds those
same 15 ids once, canonically. 108's and 109's `Commands` sub-assets are thin
reference lists into that pool (`AssetBase+_disableChildAssetParenting: true`
on both 832 and 835 — confirmed by direct read of the dump), not separate
copies of the commands.

### 3b. Our package, `1bynd_19_20027_v1_0_0.pkp`

Same three-collection shape, now with 33 elements throughout:

- Pool (object 30, array 85): all 33 ids — the original 90-104 plus the 18
  new ones (1845, 1904, 1963, 2022, 2081, 2140, 2199, 2258, 2317, 2376, 2456,
  2536, 2616, 2710, 2888, 3068, 3142, 3222).
- Model 108 ("IV-CAM-I12", array 1333): **all 33**, identical set to the pool.
- Model 109 ("IV-CAM-I20", array 1365): **all 33**, identical set to the pool.

**`build_i20_assets.py`'s `clone_command` explains why**: it calls
`self.command_collections()` and appends every newly cloned command to *every*
collection that lists commands (`pkp_asset.py:218-219`) — which walks all
objects whose class contains `IDriverCommandAsset` and starts with
`Extron.Configuration.Core.Assets.AssetBase`, i.e. the pool **and** both
per-model `Commands` sub-assets, with no per-model targeting. So every command
this script adds lands on both models automatically; nothing chose to exclude
I12 from anything.

### 3c. Answering the literal question: can a `.pkp` carry a different command set per model?

**Yes — structurally, with no new machinery.** The pool (object 30) and each
model's `Commands` sub-asset (832/835 here) are three *separate* list objects
in the graph, each independently holding `$ref`s to the same underlying
`DriverCommandAsset` objects. Extron's own donor already relies on this: it
gives PTZ-IP12 and PTZ-IP20 separate array objects, populated with the same
object identities in different order — the mechanism for "this model's list
doesn't have to equal that model's list" is already exercised by Extron,
just not (in the donor) to actually omit anything. `tools/pkp_asset.py`
already exposes the primitive needed to do it on purpose:
`CommandGraph.detach(parent_id, child_id)` (`pkp_asset.py:235-253`) removes
one child reference from one parent's collection without touching the pool or
the other model — it is a generic per-collection remove, already used
elsewhere in this codebase for a command's own child parameters, and nothing
stops it from being called with `parent_id=108` (the I12 model asset) instead.

## 4. Recommendation

**Give IV-CAM-I12 its own trimmed command surface; do not drop it from the
package.** The two candidates the task poses aren't actually the only two
options, and the evidence gathered here favors a third: keep both models,
keep the shared script and shared command *objects* (matching both the Extron
donor's own pattern, §3a, and Crestron's own shipped driver, which lists
`"supportedModels":["IV-CAM-I20","IV-CAM-I12"]` in one package —
`samples/Crestron 1 Beyond IV-CAM-i12_i20/.../Camera_Crestron-1-Beyond_IV-CAM-I20_IP.dat`),
but stop handing I12 three commands the documentation says are I20-only.

**Concrete build changes**, all in `build_i20_assets.py` after `build()`'s
existing command-creation loop, using the model ids already read once
(`g.objects` keyed by `_ver`'s owner, or simply the two ids the existing
`_bump_model_version` walk already finds — 108 and 109 are stable across
rebuilds because nothing before this point renumbers them):

1. **Detach from I12 only** (leave the pool and I20 alone):
   `TrackingMode` (§1b row 2 — Reserved-Presets.md:68-78,
   Presenter-Tracking-Settings.md:27), `TrackingProfile` (§1b row 10 —
   Reserved-Presets.md:156-178), `PresetZone` (§1b row 11 —
   Reserved-Presets.md:132-154). Call
   `g.detach(model_id_for("IV-CAM-I12"), g.commands()["TrackingMode"])` and
   the same for `TrackingProfile`/`PresetZone` — three `detach()` calls,
   using the primitive already in `pkp_asset.py` (§3c), no cloning needed.
2. **Open question to settle before touching I20's array**: §1c's spec-sheet
   asymmetry (I12Specs names Intelligent Switching; I20Specs does not) points
   at `IntelligentSwitching`/`CameraOutput`/`CameraConnectionStatus`
   potentially being the ones that need detaching from **I20**, not I12 —
   this file does not resolve that; it is a companion question this same
   3-collection mechanism can answer the same way once resolved.
3. **Leave `Identify` alone** — the only source for it (Crestron's compiled
   schema) already asserts both models, and nothing in the public docs
   contradicts that (§1b row 6).
4. **Leave `ZoomPosition`, `PanTiltAngle`, `PanAngleStatus`, `TiltAngleStatus`,
   `IndicatorLight`, and the 15 baseline commands untouched** — every one of
   these was either confirmed identical across models or is equally
   provisional on both (§1d, §1e, §1f); trimming them would remove
   accuracy, not add it.
5. **Optional, lower priority**: replace `IntelligentSwitching`'s "Resume"
   byte sequence with the I12-scoped preset 84 route (`8x 01 04 3F 02 54 FF`,
   §2) instead of the unqualified `c2` route, since 84 carries an explicit
   I12 citation the `c2` command doesn't. This changes *bytes on the wire*,
   not just graph membership, so it is a `build_i20.py` edit (a new
   `[PATCH]`), not a `build_i20_assets.py` one, and needs its own verification
   pass — out of scope for this research-only pass but worth flagging as the
   next concrete step if TrackingMode's PROTOCOL.md-style hardware
   verification path is ever extended to Intelligent Switching.

None of this requires cloning new `DriverCommandAsset` objects, a second
script, or a second `.pkp` — the package format already supports exactly the
"one script, one command pool, per-model membership list" shape this
recommendation asks for, because Extron's own donor and Crestron's own
shipped I-series driver both already use it.
